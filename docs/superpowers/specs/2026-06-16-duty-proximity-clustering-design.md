# 設計仕様: 希少＋手当業務の近接クラスタ回避（サブプロジェクトB）

**日付**: 2026-06-16
**対象**: `shift_scheduler/src/schedulers/day_scheduler.py`（`_schedule_one_day`）
**出典**: 人手修正済み最終版 `2026年6月勤務表.pdf` の配置間隔パターン

## 背景・目的

人手で仕上げた最終版（2026年6月）を観察すると、希少業務・手当業務は同一個人に
近接した日へ固めず、数日おきに回している。例：

- HB（川向）: 07→11→13→22→25 日（間隔 4/2/9/3 日）。厳密な最小間隔ではなく
  「近接クラスタを避ける」緩い分散。
- 超遅（棚町）: 03→06→09 日（約3日おき）。

現コードは HB/DR/ア に限り連続抑制（2連許容/3連阻止）を持つのみで、手当業務
（ポ/超遅/ク遅/M遅）・OP には時間的分散の仕組みが無い。本サブプロジェクトは
この「近接クラスタ回避」を希少＋手当業務へ一般化する。

## スコープ

**対象業務**: `HB`, `DR`, `ア`, `ポ`, `超遅`, `ク遅`, `M遅`, `OP`

**対象外**（明示）: CT・ク等の高ボリューム業務、および専従（病CT専従T001・
MRI専門・PET/RI/放治/館山）。対象業務は専従が存在しないため自動的に問題化しない。

## 設計

### ゴール定義
「同一業務の最小間隔を強制する」のではなく「近接した日にクラスタさせない」を
ソフト制約で誘導する（ユーザー確定：近接クラスタ回避・段階式）。

### メカニズム
`_schedule_one_day` 内、対象業務の候補 `x[s.id, l_code]` の `base_score` に対し、
`assignment_history`（最大3日前まで）を参照して「同一業務を最後に担当した日からの
間隔」に応じた段階的減点を加える。

| 直近の同一業務担当 | 減点（負のスコア） |
|---|---|
| 前日（連続）          | 強  `-120000` |
| 中1日（2日前に担当）  | 弱  `-30000`  |
| 中2日（3日前に担当）  | 微弱 `-12000` |
| 中3日以上（≥4日前）   | なし `0`      |

- 最も直近の occurrence を1つだけ採用（多重加算しない）。
- 減点幅は **配置不足ペナルティ(5,000,000) ・ SR人数下限(3,000,000) より必ず小さく**
  保つ。これにより、他に担当できる有資格者がいない日は連続を許容してカバレッジを
  死守する（ソフト制約）。

### 既存コードの一本化
現状の HB/DR/ア 専用の連続ブロック：

```python
if l_code in ['HB', 'DR', 'ア']:
    base_score = max(base_score, 30000)
    _did_yest = ...
    _did_2ago = ...
    if _did_yest and _did_2ago: base_score -= 150000   # 3連続阻止
    elif _did_yest: base_score -= 8000                 # 2連続軽抑制
```

を、対象集合（希少＋手当）に共通適用する**段階式近接クラスタ減点ヘルパー**へ
置換・統合する。HB/DR/ア の希少スキル最低保証（`base_score = max(.., 30000)`）は
維持し、減点はその後に適用する。

### 実装イメージ（確定ではなく方針）

```python
PROXIMITY_DUTIES = ('HB', 'DR', 'ア', 'ポ', '超遅', 'ク遅', 'M遅', 'OP')

def _proximity_penalty(staff_id, l_code, assignment_history):
    """同一業務の近接クラスタに対する段階的減点（負値）を返す。"""
    if l_code not in PROXIMITY_DUTIES or not assignment_history:
        return 0
    h = assignment_history
    if len(h) >= 1 and h[-1].get(staff_id) == l_code:
        return -120000   # 前日（連続）
    if len(h) >= 2 and h[-2].get(staff_id) == l_code:
        return -30000    # 中1日
    if len(h) >= 3 and h[-3].get(staff_id) == l_code:
        return -12000    # 中2日
    return 0
```

呼び出し側で `base_score += _proximity_penalty(...)`。

## エラー処理・エッジケース
- `assignment_history` が短い月初は `len()` ガードで安全。
- 候補がその業務で1名しか居ない日は減点後も配置不足(5M)が支配し、必ず充足される。
- 専従/保護対象は対象業務に含まれないため影響なし。

## 受け入れ基準（検証）
2026年7月を再生成し、以下を満たすこと：
1. **既存HB状態を壊さない**: HB担当 ≈10名 / 最多 ≈5回 / 最大連続 ≤2 を維持。
2. **手当業務の近接クラスタ低減**: ポ/超遅/ク遅/M遅 で同一個人の連続・2日内クラスタが
   修正前より減少（連続回数の合計で比較）。
3. **代休 非悪化**: 代休 ≤ 1.5日（Plan B基準）を維持。
4. 全ハード制約（配置不足ゼロ・SR人数下限・連勤≤6）維持。

## 非目標（YAGNI）
- 業務別の精密な間隔チューニング（案2）は採用しない。
- ハード最小間隔制約（案3）は採用しない（実行不能リスク）。
- CT/ク等の高ボリューム業務への適用はしない。
