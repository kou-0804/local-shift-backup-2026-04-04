# 手当業務（ポ/超遅/ク遅/M遅）の回数分散・連続回避 設計

**日付:** 2026-06-17
**対象:** `shift_scheduler/src/schedulers/day_scheduler.py`
**背景:** 2026年7月勤務表で「ポ」(ポータブル)が特定者へ集中（星=5回・池田=4回）し、
連続も発生。手当（手当金）に関わる勤務のため、回数分散と連続回避を徹底する。

---

## 1. 現状の「ポ」制約（確認結果）

| # | ルール | 種別 | 内容 |
|---|---|---|---|
| 1 | 需要（勤務場所マスタ） | 必須 | ポ=2人/日（月〜土）、日曜0 → 月約52枠 |
| 2 | PB-01 最低ランク `ポ,B,1` | ソフト | 毎日Bランク以上を最低1人（不足スラック減点300万） |
| 3 | PB-04 / SR-07 D同士禁止 | ハード | Dランク2人組み禁止（実質 1B+1any） |
| 4 | 夜勤当日ポ禁止 + 17業 | ハード | `ban_mg_po` |
| 5 | 近接クラスタ回避 `_proximity_penalty` | ソフト | 前日=-12万／2日前=-3万／3日前=-1.2万 |
| 6 | 回数公平化（手当）`WEIGHT_PAID` | ソフト | 平均超過 重み6万／0回者+10万（上限150万） |

**有資格者:** Bランク17名・Dランク14名（計31名）。「-」40名はベテランで対象外。

## 2. 偏りの真因

- 資格者は十分（B17/D14）。**PB-01（Bランク必須）は阻害要因ではない → 撤廃しない。**
- 真因は **(a) 回数上限が無い**、**(b) 公平化6万・連続12万が配置充足(500万)に比べ弱い**。
- 結果、特定者（星・池田）が繰り返し選ばれ、連続も残る。

## 3. 決定事項

- **1人あたり月間上限：3回**（目標2回）。
- **連続回避：中1日以上空ける**（前日連続を実質禁止）。
- 対象は手当業務 `PAID = (超遅, ポ, ク遅, M遅)`。HB/DR/ア/OP は現状維持（カバレッジ保護）。

## 4. 実装方針（day_scheduler.py、グリーディの累積カウントで制御）

すべてソフト制約。減点は配置充足(500万)・SR人数下限(300万)より必ず小さく保ち、
**「分散のために人員不足を招かない」** を厳守する（最終手段では連続・超過を許容）。

### A. 1人あたり回数上限（新規）
`base_score` 加算（スコア計算ループ内、`l_code in PAID` のとき）:
- `p_count = assignment_counts[s.id]['_L_'+l_code]`（その業務の累積回数）
- `p_count == 2`（3回目）: `-150,000`（緩い抑制、上限3回までは許容）
- `p_count >= 3`（4回目以降）: `-2,000,000`（準禁止。ただし500万＜なので最終手段では可）

### B. 連続回避の強化（`_proximity_penalty` を手当業務だけ強化）
`PAID` のとき:
- 前日連続: `-12万` → **`-800,000`**（中0日＝連続を実質禁止）
- 2日前（中1日）: `-3万` → **`-150,000`**（中1日も抑制し中2日以上を誘導）
- 3日前（中2日）: `-1.2万` → `-40,000`
- HB/DR/ア/OP は従来値のまま（変更なし）。

### C. 公平化重みの引き上げ（補助）
`WEIGHT_PAID` 60,000 → **100,000**（超過者を更に押し出す。上限150万は据置）。

## 5. 影響範囲・リスク

- 変更は `day_scheduler.py` のみ（`_proximity_penalty` と スコアループ）。
- リスク: 上限3＋連続禁止＋夜勤禁止の重なりで、ポ2枠/日が一部埋まりにくくなる可能性。
  → すべてソフトのため最終手段で充足優先（INFEASIBLE化しない）。
- 検証: 再生成後の出力で ポの「最大回数」「連続(maxrun≥2)件数」「人員不足スラック」を確認。
  目標: ポ最大回数 ≤ 3、連続(maxrun≥2) = 0、人員不足の新規発生なし、代休増なし。

## 6. 非対象（YAGNI）

- PB-01/PB-04 等のハード制約の撤廃（資格者十分のため不要）。
- 鬼バランサー(Phase 2.5)の改修（ポは場所固定で再配置対象外。検証で問題なければ触らない）。
